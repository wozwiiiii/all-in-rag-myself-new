## 二、架构实况（已验证属实的部分）

### 分层与依赖

```
app/api/         装配层：路由/认证/限流/探针        124 + 150 行
app/orchestrator/ 编排层：意图路由 + 分支调度       243 行
app/rag/         领域层 A：chunk→ingest→bm25→retriever→generator   650 行
app/tabular/     领域层 B：loader→schema→agent→sandbox             812 行
app/llm/         基础设施：chat/rerank/embed 统一收口               226 行
app/core/        基础设施：config/logging/errors                   177 行
```

依赖方向经抽查确认无倒置：`core` 不 import 任何业务模块；所有 LLM 调用只走 `llm/client.py`。

### 三条主链路

- **RAG**：构建期（scripts/build_index.py）与服务期分离；查询期向量全量 cosine top-20 ∪ BM25 top-20 → 向量阈值过滤 → rerank 精排 → top-6
- **表格**：LLM 选表 → 注入所选表 schema 画像 → ReAct 文本协议循环 → AST 校验 → 子进程沙箱执行 → traceback 回填自愈（≤8 轮）
- **编排**：LLM 意图分类（超时/失败降级启发式）→ 单路或 hybrid 并行 → LLM 融合

### 确实做得好的设计（客观评价）

1. **降级链完整且可审计**：BM25 失败→纯向量、rerank 失败→RRF、路由失败→启发式、hybrid 单路失败→幸存路返回，**每层都有独立日志关键字**。这在同类项目中不常见。
2. **沙箱纵深防御**：AST 静态白名单 + 运行时 curated 命名空间（`pd.io`/`np.memmap` 物理不存在）+ 子进程隔离超时强杀。30 条攻击载荷静态+运行时双重拦截，实测通过。从黑名单演进到白名单是真实的红队驱动。
3. **阈值拒答语义稳定**：BM25-only 候选也必须过向量 cosine ≥0.35，加 BM25 不改变拒答行为——避免了"改检索把拒答改坏"的典型回归。
4. **构建/服务分离 + embedding 缓存**：增量重建近乎免费。

## 三、核心问题：评分指标已饱和失效（P0）

### 事实链

**① `eval/dataset.jsonl` 字段只有 `id/category/question/keywords`，`reference` 字段 0/18 存在。**

```python
# eval/metrics.py:41-42
def semantic_score(answer, reference, llm):
    if not reference:
        return 0.5          # ← 全部 18 题都走这一支
```

**② 实际生效的公式退化为一个只数关键词的计数器：**

```
score = 0.7 × 关键词命中率 + 0.3 × 0.5
      = 0.7 × 关键词命中率 + 0.15
```

**③ 单项理论上限是 0.85，不是 1.0。**

**④ R8 报告里 16 道非拒答题得分全部恰好等于 0.850——全部撞上天花板。**

反推验证：

```
(16 × 0.85 + 2 × 1.0) / 18 = 0.8667   ← 与报告总平均分精确吻合
```

**所以 0.8667 的真实含义是"16 道题关键词 100% 命中 + 2 道拒答题满分"，不是"系统拿到了 86.7 分"。这个评测集已经无法分辨任何进一步的改进。**

### 连带问题：R8 的提升存在循环论证

wiki 把 R8（两遍生成）的 +0.04 描述为"结构性改善"。但把三件事放在一起看：

| 环节 | 代码/数据中的事实 |
|---|---|
| 抽取 prompt | `generator.py:32` 明确写"**完备性优先：宁可多抽不可遗漏**" |
| 答案构成 | `generator.py:161` 要点**程序化拼接**为零丢失答案主体 |
| 评分方式 | 指标只统计关键词字符串是否出现 |

**三者叠加，关键词命中率趋近 100% 是设计上的必然结果，而非答案质量提升的独立证据。**
更关键的是：指标只测"覆盖"不测"精确率"，而抽取 prompt 鼓励过度抽取——**这个指标正在奖励"多说"，惩罚"精炼"**。

wiki 08 章自己写道："下一步是扩评测集，不是继续加特性"。但实际做的是加了特性（两遍生成），把评测集撑到饱和。**项目自身的方法论与执行出现了不一致**——这在面试中如果被追问，是比"分数不高"更难解释的问题。

## 四、次级问题

### 4.1 路由正确率统计有结构性缺陷

```python
# eval/run_eval.py:80
"expected_route": item["category"],   # refuse 类 → expected_route = "refuse"
```

Router 只输出 `text/table/hybrid`，**永远不可能输出 `refuse`**。因此 refuse 类 2 题的"路由正确数"恒为 0，与系统能力无关。

- R8 报告显示 refuse 类"路由正确数 0/2"，总分 1.000（拒答是对的）
- wiki 06 声称"全程七轮评测路由 18/18" → **与报告实测的 16/18 不符**

**修复方向**：refuse 类不参与路由正确率统计，改为统计"是否正确拒答"（当前实际是 2/2 满分）。

### 4.2 延迟已在红线附近

R8 实测耗时：

| 题 | 耗时 | 类别 |
|---|---|---|
| Q3 | **54.4s** | text |
| Q7 | **48.7s** | text |
| Q15 | **55.4s** | hybrid |
| text 8 题均值 | **~28s** | — |
| table 6 题均值 | ~17s | — |

120s 总超时下，text 类最慢题已用掉 45%。两遍生成每题固定 +6 次并行抽取调用 + 1 次结论段调用。wiki 声称"延迟反而下降"只在 Q1/Q3 相对 map-reduce 版本成立，绝对水位仍偏高。

### 4.3 文档口径不一致（影响可信度）

- 测试数：82（01/09/README）vs 88（07/08）→ 实测 88
- 评测轮次：六轮（README/01）vs 八轮（07）→ reports 目录 10 份文件
- wiki README 未提及指标失效这一已知限制，而 08 章"诚实边界"节是项目最诚实的亮点——**恰恰漏了最关键的一条**

## 五、后续开发路线（按优先级）

### P0 · 修尺子 —— 不修，后面所有工作都无法证明价值

| # | 动作 | 验收标准 |
|---|---|---|
| 1 | 为 18 题补 `reference` 标准答案，让 0.3 语义权重真正生效 | `semantic_score` 不再恒定返回 0.5，分数分布出现差异 |
| 2 | 修 `expected_route`：refuse 类移出路由正确率，改统计拒答正确率 | 报告中 refuse 类不再显示 0/2 |
| 3 | 评测集扩到 **60–100 题**，分层覆盖（术语精确匹配 / 语义推理 / 跨表关联 / 拒答 / 多跳） | 重跑噪声 ≤ ±0.01 |
| 4 | 固定评测协议：多次跑取均值、记录模型版本与温度 | 报告头部携带可复现元信息 |

> 若决定**不**补 reference，就应诚实宣布改用纯关键词指标，并在报告中标注上限为 0.85——把 0.85 当满分看，而不是把 0.8667 当 86 分看。

### P1 · 补上"正确性"维度

当前指标**只测有没有说到，不测有没有说错**。对危化品应急场景，"答得全但答错一条"比"答得少"危险得多。

- 引入 faithfulness / 事实一致性检查（可先做规则版：答案中的数字、条款编号是否能在召回 chunk 中找到出处）
- 引入**冗余惩罚**：要点数与命中数之比，防止过度抽取刷分
- 目标指标：`score = 覆盖 × 正确性 × (1 - 冗余惩罚)`

### P2 · 降延迟

- 抽取轮是纯抽取任务，用 72B 是浪费 → 换成小模型（7B/14B）做抽取，保留 72B 只做结论段
- 结论段 + 要点的结构已确定性，可考虑要点去重合并（跨 chunk 重复要点当前会并列出现）

### P3 · 工程化补齐

- 限流改 Redis（当前单实例内存，接口已收敛在 `security.py`，替换面小）
- 沙箱 OS 级降权（容器非 root / seccomp）
- `.doc/.wps` 5 篇文档支持（当前如实跳过）
- 检索在 10^5+ chunk 时切回 Chroma query + id 映射（注释已写，代码未实现）

### P4 · 简历与面试呈现

**当前最值钱的故事不是"我加了 BM25"，而是"我发现自己的评测指标饱和了，然后修了它"。**

后者体现的是度量意识与自我证伪能力，比任何单项技术点高一个层级。建议顺序：

1. 先完成 P0（修指标 + 扩评测集）
2. 用"R8 后指标饱和 → 我诊断出 reference 缺失 → 修复后重测"作为完整闭环故事
3. 再谈检索/生成优化，且每个优化都必须能说清"为什么它不在噪声内"

**工程质量（架构分层、降级链、安全沙箱）确实扎实，88 项测试全绿，值得肯定；但度量体系已经饱和失效——0.8667 是天花板而非成绩单，R8 的提升存在循环论证。当前最该做的不是加特性，是把尺子修好。**
