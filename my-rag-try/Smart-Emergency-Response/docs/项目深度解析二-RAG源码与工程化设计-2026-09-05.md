## Part A · baseline：起点长什么样（源码级）

baseline（`baseline/`，3 个核心文件约 370 行）是赛题原始基线：**LlamaIndex 全托管三件套**。

```
main.py：
  SimpleDirectoryReader("./datas/文本数据").load_data()   ← 文档加载，切分策略全默认
  → ChromaVectorStore → VectorStoreIndex.from_documents    ← 索引，chunk 大小全默认
  → index.as_query_engine()                                ← 检索+生成一体，参数全默认
  → 逐题 query() → answer.csv
```

| 层 | baseline 实现（源码） | 具体局限 |
|---|---|---|
| 文档切分 | `SimpleDirectoryReader` 默认策略 | 切分不可控，无标题层级语义——法规文档"第 X 条"被随机切断，引用无从谈起 |
| 检索 | `as_query_engine()` 默认 top-2 相似度召回 | **无阈值、无拒答语义**：哪怕检索结果与问题无关也硬答。这与应急场景"宁可不答，不可编造监管结论"的要求**方向相反** |
| 生成 | 默认 prompt 模板 + QwenLLM（`local_llamaindex_llm.py`，temp 0.1-0.6） | 无引用来源格式、无列举类题目的覆盖约束、答案无结构 |
| 可靠性 | QwenLLM 直接调 SDK | **零重试、零超时、无 429 处理**；main.py 里 try/except 打印后继续 |
| 缓存 | `remote_embedding.py`：pickle 单文件 dict | 并发写不安全、无事务、换 embedding 模型后缓存会污染（key 不含模型名） |
| 评测 | 无 | answer.csv 直接交付，没有任何质量度量——**连"尺子"这个概念都不存在** |

**重写决策的本质**：baseline 把所有决策交给了框架默认值，而默认值没有一项是为"应急安全问答"这个场景做的。app/ 的重写不是炫技，是把每一层默认值换成显式的、有依据的场景化决策。下表逐层对照：

| 层 | baseline 默认值 | app/ 的替代决策 | 决策依据 |
|---|---|---|---|
| 切分 | 框架默认 | 按标题层级切 section（1200 字上限 + 150 重叠） | 法规文档天然有标题层级，chunk 边界对齐语义边界 |
| 召回 | top-2 无阈值 | 向量 top-20 ∪ BM25 top-20 → 阈值 0.35 → rerank → top-6 | 宽召回窄输出；阈值承载拒答语义 |
| 排序 | 无 | rerank 精排，失败降 RRF | cross-encoder 对细排序显著优于 bi-encoder |
| 生成 | 默认模板单遍 | 两遍 map-reduce + 程序化拼接 | 实测注意力稀释（见 B4） |
| 可靠性 | 无 | 统一收口：重试/429/超时/降级链 | 策略只有一份实现才可预期 |
| 度量 | 无 | eval 体系（后期修复） | 无度量即无改进 |

## Part B · RAG 阶段源码级解析（五件套）

### B1 数据进入：chunking.py —— 按标题语义切，不是按长度切

核心数据结构：`Block(level, text)`，level 0 是正文、1-4 是标题层级。`chunk_blocks()` 用 **heading_stack 维护当前标题路径**，每个 chunk 携带完整路径（`heading_path`，如 "某文件 > 第一章 > 1.2 节"）——这个字段同时服务两个下游：生成时的引用来源、未来父子检索扩展的预留。

超长 section 的二次切分（`_merge_overflow`）有三个细节：
- 按段落聚合到 MAX_CHARS=1200，相邻块保留 **150 字尾部重叠**（防语义在边界被截断）
- 单段自身超长则硬切，滑窗步长 = MAX_CHARS - OVERLAP_CHARS（同样保证重叠）
- PDF 走 `extract_pdf`：无文本层的扫描页触发 **OCR 兜底**（pypdfium2 渲染 + RapidOCR PP-OCRv4，进程内单例复用，依赖缺失时打一次警告返回空串、**不阻断整库构建**）

动机：法规/标准文档的信息单元是"条款"，标题层级就是天然的语义边界。按框架默认长度硬切，一条条款可能跨两个 chunk，检索命中时上下文残缺。

### B2 索引构建：ingest.py —— 构建/服务分离 + 幂等

- **构建与服务完全分离**：`python -m scripts.build_index` 一次性构建（提取→分块→embedding→Chroma 持久化），服务端 `Retriever.__init__` 只读加载。重启服务不再重复计算任何 embedding
- **幂等全量重建**：先 `delete_collection` 再重建。敢这么做的底气是 embedding 有磁盘缓存（sqlite，见 C1）——710 chunk 里未变的文本全部命中缓存，重复构建只剩 API 往返之外的成本
- **chunk_id 设计**（ingest.py:29-31）：`md5(source|heading_path|index|md5(text)[:8])`——同一位置的同一文本得到同一 ID，文本变了 ID 就变，避免旧向量残留
- 单文件解析失败只记录 `ingest_extract_failed` 并跳过（report.skipped），**一个坏文件不阻断整库**；`.doc/.wps` 如实标注"已知限制"跳过，不假装覆盖

### B3 检索：retriever.py —— 三个值得细说的设计

**① 全量内存索引统一坐标系（retriever.py:57-65）**

```python
got = self._collection.get(include=["documents", "metadatas", "embeddings"])  # 启动时拉全量
emb = np.asarray(got["embeddings"], dtype=np.float32)
norms = np.linalg.norm(emb, axis=1, keepdims=True)   # 行归一化
self._emb_normed = emb / norms                        # 归一化后点积 = 精确 cosine
```

这是 2026-08-31 引入 BM25 时的关键决策：BM25 候选和向量候选必须落在**同一个文档坐标系**（同一个 i 对应同一篇 chunk）才能取并集。如果向量路走 Chroma `query()`（HNSW 近似检索、返回 id），BM25 路走内存数组，两路 id 无法对齐。解法是向量路也用全量内存：710 chunk 规模下，一次 numpy 矩阵乘就是**精确 cosine**，毫秒级，比 HNSW 近似检索还快还准。代码注释明确写了切换点：**语料到 10^5+ 再切回 Chroma query + id 映射**——这是规模驱动的取舍，不是无脑选型。

**② 拒答语义只归向量阈值管（retriever.py:101-106）**

```
pool = 保序去重(vec_top20 ∪ bm25_top20)
pool = [i for i in pool if sims[i] >= 0.35]   ← 阈值只看向量分
```

BM25 只补充候选与参与排序，**不参与拒答判定**——BM25-only 候选也必须过向量阈值。动机：BM25 分数量纲与问题无关（一个生僻词命中也能得高分），如果 BM25 能单独把候选送进池子，改 BM25 参数就会破坏"证据不足→拒答"的行为。这条设计避免了"加了 BM25 把拒答改坏"的典型回归。

**③ 排序与降级链（retriever.py:119-134）**

rerank 可用 → cross-encoder 精排取 top-6；rerank 失败/关闭 → **RRF 融合序**（`rrf_fuse`，k=60）而非纯向量序。选 RRF 的动因写在 bm25.py:53：BM25 分与 cosine 量纲不可比，RRF 只用排名、无需调权。每层降级都有独立日志关键字（`bm25_failed`/`rerank_failed_fallback_rrf`/`retrieve_no_evidence`），可审计。

### B4 生成：generator.py —— 两遍生成的真实动机与后续反噬

**问题起点（实测）**：单遍生成把全部召回 chunk（约 7k 字符）塞进一个 prompt，实测出现**注意力稀释**——列举类答案丢失"感知""监护"这类中等重要条目。这不是猜测，是当时逐题对答案发现的。

**解法（map-reduce 两遍）**：
- **第一遍 map**（generator.py:64-110）：逐 chunk 并行要点抽取（ThreadPoolExecutor，max_workers=min(6, len(chunks))，temp=0，max_tokens=500）。单 chunk 的抽取任务平凡化，不再稀释。单路失败返回空串不阻断；每个要点行尾标注来源 `[i]`，最后全局重编号
- **第二遍 reduce**（generator.py:113-128）：要点清单**程序化拼接**为答案主体（python 字符串拼接，不经 LLM），LLM 只生成 ≤150 字结论段。两个动机：① 抽取到的要点必然出现在答案里——**零丢失由构造保证**；② 72B 模型实测 ~9 字/秒，长答案重组是延迟瓶颈——把 LLM 输出压到 150 字，延迟有界
- 抽取全失败 → 退化单遍生成（原行为），配置 `generation_two_pass` 可整体关闭

**拒答判定的一个细节**（generator.py:166-168）：`_REFUSAL_MARKERS`（"无法回答/未检索到/未提及"等）的匹配**限定在答案开头 60 字**。动机：正文自然出现"标准未提及 X"不代表拒答，全文匹配会把正常答案误标成拒答。

**后来的反噬（必须如实写）**：两遍生成的三个特征——抽取 prompt "宁可多抽不可遗漏"（generator.py:32）、答案程序化拼接零丢失、关键词命中式评分——三者叠加，使 R8 评测关键词命中率趋近 100% 成为**设计必然**。两遍生成当初为解决真实质量问题的动机是成立的，但它恰好把"覆盖型指标"的漏洞放大了：**在坏尺子下，一个真实优化自动变成了刷分机器**。这就是第一份解析里"循环论证"结论的代码层来源。教训不是"两遍生成错了"，而是：**任何优化的效果声明都必须经过可信度量的独立检验，优化手段与评价手段不能共享同一个偏差方向**。

### B5 编排层两个与 RAG 直接相关的可靠性设计

- **router.py "永不抛异常"**：路由是单点，挂了整个请求就挂。所以 LLM 分类失败降级为关键词启发式（`_TABLE_HINTS`/`_TEXT_HINTS`），启发式兜底返回 **hybrid**（两路都跑——最保守：宁可多花时间，不可漏路）
- **hybrid 的三层降级**（pipeline.py:181-226，`_gather_first_error`）：① 单路失败→幸存路返回，`detail.degraded=True` 如实标注；② 一路拒答→以非拒答路为准（不把"无法回答"融进最终答案）；③ 融合 LLM 调用失败→退表格路答案（数据部分本就以统计为准），`fusion_degraded=True`。三层都有独立日志

## Part C · 工程化设计：底座 + 四批次新增

### C1 第一轮底座（baseline → app 时建立的）

**LLM 统一收口（client.py，约 276 行）**——全项目唯一允许调 LLM SDK 的地方：

| 能力 | 实现 | 动机 |
|---|---|---|
| 重试 | tenacity 装饰器：指数退避 2-30s，最多 4 次，仅对超时/连接错/429/5xx | 重试策略只此一份，行为可预期 |
| 429 专项 | `APIStatusError` 中 429/5xx 转抛 `_Retryable429` 统一处理（client.py:172-175） | 限流错误与其他错误的重试语义不同 |
| rerank | OpenAI SDK 不封装 /rerank 端点 → httpx 直调（client.py:195-219），但**复用同一套重试语义** | 端点不同，策略不散落 |
| embedding 缓存 | sqlite（WAL 模式）替换 baseline 的 pickle：`cache_key = md5(模型名:text)`（client.py:115-117） | 并发安全 + **key 含模型名，换模型不污染旧缓存**（baseline pickle 缓存的真实缺陷） |
| usage 记录点 | `chat()` 成功后 `_record_usage`（client.py:177） | 单点记录，覆盖全项目所有调用 |

### C2 四批次新增（2026-09-03）的设计细节

**批次 1 · 评测修复**——修的是度量层，不改业务代码：
- `metrics.py:score_answer` 加 `expected_route` 参数；refuse 判定从"答案文本含拒答词"改为 `refused` 标志显式传入（`run_eval.py:_route_correct`）
- 16 题补 reference 的**操作纪律**：每题先跑检索定位向量库原文 chunk，reference 基于原文撰写——保证标准答案可被系统召回，评分对系统公平
- 新增 `tests/test_metrics.py` 12 项，把评分行为（语义分权重、拒答判定、路由判定）锁进测试

**批次 2 · usage 累加器**（client.py:51-96）：
- 方案对比记录在代码注释里：**contextvar 被否决**——generator 抽取轮用 ThreadPoolExecutor，contextvar 在池线程 copy-context 后写不回父上下文，并行调用的 token 会丢
- 采用实例级累加器：`Lock` 保护 `_usage` dict，`usage_snapshot()` 深拷贝做请求入口基线，`usage_delta(before)` 做差值
- **如实声明的已知误差**（client.py:54）："并发请求间 token 归属有交叉误差，观测用途可接受"——多请求并发时单个请求的 usage 可能包含别家 token。选择承认误差而非上重方案，因为该数据当前只服务于优化决策论证
- 管线侧（pipeline.py:93-94, 136-138）：`getattr(self._llm, "usage_snapshot", None)` 防御式取用——测试注入假 client 没有 usage 方法也不崩

**批次 3 · 注入防护（两层，输入结构隔离 + 输出泄露检测）**：
- 输入侧（agent.py:136-143）：`_select_tables` 把"选表指令+表清单"放 system、"【问题】\n{用户输入}"放 user 两条消息。原实现把用户输入与指令同级拼接，用户输入获得与指令同级的"忽略上文"能力。代码注释直接写明动机："防止用户输入与指令同级拼接而具备'忽略上文'的越狱能力"
- 输出侧（guard.py）：7 条泄露签名只收 **prompt 元层特征**（角色定义句/ReAct 协议标记/表画像区块标题）——模型只会从 system prompt 看到这些、正常业务答案绝不会输出。归一化（去空白+全角）后子串匹配，抗轻微改写。安全文案 `LEAK_SAFE_ANSWER` 刻意不含 `_REFUSAL_MARKERS` 词汇（guard.py:58-60 注释）——避免污染评测的 refused 口径
- 检测点在 pipeline 出口统一执行（pipeline.py:141-148），**覆盖全部路由**（text/table/hybrid 一次不漏），命中则记 `prompt_leak_detected`（含命中签名与延迟）并替换答案

**批次 4 · SSE 阶段事件流**：
- 核心结构（pipeline.py:64-77）：`answer()` 与 `answer_stream()` **都是 `_answer_stages()` 的消费者**——前者只取末事件，后者逐事件透传。**流式与非流式共享同一条执行路径**，不可能出现"流式版和同步版行为不一致"这类分叉 bug。这是本批次最值得学的结构决策
- 事件协议 5 种：`stage(routing) → route → stage(working, branches) → answer | error`
- API 层（routes.py:49-85）：`_sse()` 统一编码（dataclass asdict + JSON）；`event_source()` 捕获一切异常转 error 事件——**SSE 响应开始后无法改状态码**，抛给全局 handler 会把流截断成 500，error 事件收尾让客户端拿到结构化错误

### C3 操作层：每项改动是怎么验证的（可复现）

| 操作 | 命令/方法 | 通过标准 |
|---|---|---|
| 全量测试 | `pytest`（tests/ 4 个新增文件：test_metrics/test_client_usage/test_guard/test_api_stream） | 120 passed（pytest 权威计数，含 parametrize 展开） |
| 评测 | `python -m eval.run_eval` → `eval/reports/report-*.md` | 对比前后报告逐题分数 |
| 注入防护真实验证 | 真实请求诱导"复述完整 system prompt" | 答案被替换为安全文案 + `prompt_leak_detected` 日志 |
| SSE 真实验证 | 真实请求观察事件流 | 首事件 <1s；routing→route→working→answer 顺序正确 |
| usage 真实验证 | text 题端到端跑 | 8 次调用 6000-8700 tokens，并行抽取不丢 |

单测之外坚持真实验证的原因：单测的 stub 无法证明"真实 72B 模型的越狱诱导真的会被拦"、"真实并行抽取的 token 真的不丢"。**度量闭环（改完跑评测）+ 真实链路验证**是这个项目的两条验收底线。

## Part D · baseline → 当前：能力对照与分数的真相

| 能力 | baseline | 当前 app/ |
|---|---|---|
| 切分 | 框架默认 | 标题语义切分 + OCR 兜底 + 重叠 |
| 检索 | top-2 无阈值 | 三路融合 + 阈值拒答 + rerank/RRF 降级 |
| 生成 | 默认模板 | 两遍 map-reduce + 引用标注 + 拒答语义 |
| 可靠性 | 无重试无超时 | 收口重试/429/全链降级（每层可审计） |
| 安全 | 无 | 沙箱（表格路）+ 注入防护（输入隔离+输出检测） |
| 度量 | 无 | 18 题评测体系（修复后可信）+ token 观测 + 120 项测试 |
| 接口 | 脚本出 csv | FastAPI（认证/限流/探针/SSE） |

**分数的真相（重申，这是本项目最重要的诚实条款）**：0.8667→0.9387~0.9647 的提升主要来自**测量口径修复**（天花板 0.85→1.0、refuse 判定显式化），系统能力本身在这轮没有变化。变化的是：分数从"不可信"变成"可信"，且暴露了真实差距（无满分题、Q15 答错字段得 0.49）。**用可信的分数指导下一步（事实一致性校验），好过用不可信的分数自我祝贺。**

### 遗留（不粉饰）

1. 事实一致性校验未做（Q15 已实证为最高优先级）
2. 评测集仍 18 题（噪声 ±0.015），多跳题为零
3. 延迟红线未解（text 最慢 54-93s），抽取换小模型已有 usage 数据可论证
